Capacity Forecasting looks for where the network will "choke." In 5G, this is extremely complex because capacity is no longer just "bandwidth"—it is a combination of compute (K8s), transport (Front/Backhaul), and radio (RAN) resources.

1. Executive Summary

The goal is to provide an AI-driven "What-If" engine that predicts when and where the 5G network will exceed its capacity limits across all layers—from the physical cell site to the virtualized core. This enables proactive Capital Expenditure (CAPEX) planning and automated scaling.

2. Multi-Layer Capacity Requirements

2.1 5G RAN (Radio Access)

  • Metrics: PRB (Physical Resource Block) Utilization, User Throughput, RRC Connected Users.
  • Forecasting Goal: Predict "Cell Congestion" 3–6 months in advance to trigger new site builds or "Massive MIMO" upgrades.
  • Key Variable: Spectrum Efficiency. As load increases, spectral efficiency often drops; the model must account for this non-linear decay.

2.2 Transport Network (Fronthaul/Backhaul)

  • Metrics: Interface utilization (Gbps), Port density, Optical power levels.
  • Forecasting Goal: Ensure the "Pipe" is big enough for the RAN.
    • Fronthaul (eCPRI): Requires ultra-low latency. Forecasting must predict jitter/delay increases.
    • Backhaul: Predict when a 10G link needs an upgrade to 100G based on aggregate RAN growth.

2.3 Cloud-Native Infra (K8s/CNF)

  • Metrics: CPU/RAM headroom, etcd latency, Pod density per worker node.
  • Forecasting Goal: Predict when the Kubernetes cluster will run out of "Compute" to host new CNF instances (e.g., adding a new UPF for a private 5G slice).

2.4 5G Core (Control & User Plane)

  • Metrics: SMF (Session Management) transactions per second, UPF throughput (Gbps).
  • Forecasting Goal: Predict "Signaling Storms" or User Plane saturation during mass events (e.g., stadium concerts or morning rush hour).

4. Technical Architecture: The "Forecasting Stack"

  • Data Lake: Consolidates metrics from Prometheus (Infra), Netflow (Transport), and 3GPP Counters (RAN/Core).
  • Model: Ensemble Approach
    • Short-term (1-7 days): LSTM (Long Short-Term Memory) for auto-scaling CNFs.
    • Long-term (3-12 months): Facebook Prophet or XGBoost for hardware procurement planning.
  • Output: A "T-Minus" Dashboard showing: "Asset X will reach 90% capacity in 42 days."

5. Success Metrics (KPIs)


• Forecast Accuracy (MAPE): Mean Absolute Percentage Error should be <15%.
• Just-In-Time Provisioning: Reduction in "Over-provisioned" (wasted) hardware by 20%.
• Zero-Congestion Incidents: Zero unplanned outages caused by resource exhaustion.

2. 3GPP NWDAF: The Capacity Interface

For a standardized 5G network, you don't build custom scrapers; you use the NWDAF (Network Data Analytics Function).

2.1 Standardized Interfaces

The NWDAF provides two primary services for capacity forecasting:

  • Nnwdaf_AnalyticsInfo: A "Request-Response" service for on-demand planning (e.g., "What is the predicted load for next Monday?").
  • Nnwdaf_AnalyticsSubscription: A "Subscribe-Notify" service that pushes alerts to the Orchestrator (NSMF) when a capacity threshold is predicted to be breached.

2.2 Key "Analytics IDs" for Capacity

When requesting data from the NWDAF, your system should use these standard IDs:

  • LoadLevelInformation: Current and predicted load of a specific Network Function (NF) or slice.
  • ServiceExperience: Predicted MOS (Mean Opinion Score) which drops when capacity is saturated.
  • NetworkPerformance: Focuses on gNB (RAN) and user-plane performance metrics.
