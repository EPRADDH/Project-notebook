EMS Vibe Coding Assistant-Technical Architecture & Design Documen

1. Document Purpose

This document describes the technical architecture, system design, AI design, and implementation approach for building the EMS Vibe Coding Assistant, an AI-powered assistant integrated with an Element Management System (EMS).

2. Problem Context (Why This System Exists)

Traditional EMS platforms:

  • Require deep domain expertise
  • Use rigid UI workflows
  • Have slow fault diagnosis
  • Are error-prone during configuration changes

EMS Vibe Coding Assistant addresses this by introducing:

  • Natural language interaction
  • AI-assisted reasoning
  • Safe automation with guardrails
  • Explainable, auditable actions

3. High-Level System Goals

  1. Allow users to interact with EMS using natural language
  1. Reduce MTTR and operational effort
  1. Prevent unsafe network actions
  1. Maintain telecom-grade security and compliance
  1. Be vendor-neutral and scalable

4. System Architecture Overview

4.1 Macro Architecture

Key Principle

LLM never talks directly to EMS APIs

5. Core System Components

5.1 User Interface Layer

Components

  • EMS main screen (existing)
  • Embedded AI chat panel
  • Action preview & approval modals

Responsibilities

  • Capture user intent
  • Display AI explanations
  • Handle approval workflows
  • Render EMS data (KPIs, alarms, configs)

Tech Stack (Suggested)

  • React / Angular
  • WebSocket for real-time updates
  • RBAC-aware UI rendering

5.2 Conversation Orchestrator (Brain of the System)

Responsibilities

  • Maintain session context
  • Assemble prompts
  • Route tasks to LLM
  • Decide read vs write flows
  • Control execution lifecycle

Why This Is Critical

  • Keeps LLM stateless
  • Centralizes control logic
  • Enables auditing and rollback

Implementation

  • Node.js / Java Spring Boot
  • Stateless API + Redis for session context

5.3 LLM Reasoning Layer (AI Brain)

Role of LLM

  • Understand natural language
  • Extract intent
  • Reason over EMS data
  • Generate explanations
  • Propose actions (not execute)

Prompt Architecture

  • System Prompt (rules)
  • Domain Prompt (EMS knowledge)
  • Context Prompt (live EMS state)
  • Task Prompt (user request)

LLM Options

  • Private GPT / OpenAI (cloud)
  • Llama / Mistral (on-prem)
  • Hybrid (recommended)

5.4 Guardrail & Policy Engine (Non-AI)

Why Non-AI?

Safety must not depend on probabilistic systems.

Responsibilities

  • RBAC enforcement
  • Risk classification
  • Parameter limit validation
  • Approval enforcement
  • Action blocking

Example Rules

  • NOC → Read-only
  • Config change → Approval required
  • Reboot → Critical risk

5.5 Execution Controller

Responsibilities

  • Translate approved actions into EMS API calls
  • Manage retries and failures
  • Handle rollback
  • Normalize vendor APIs

Design Rule

LLM →JSON proposal
ExecutionController →EMSAPI

5.6 EMS Integration Layer

EMS Modules

  • Performance Management (PM)
  • Fault Management (FM)
  • Configuration Management (CM)
  • System Management (SM)

Integration Style

  • REST / gRPC APIs
  • WebSocket / streaming alarms
  • Vendor abstraction layer

6. AI Design Details

6.1 Intent Classification Model

Intent Types

  • READ_ANALYSIS
  • EXPLAIN
  • CONFIG_PREVIEW
  • CONFIG_EXECUTE
  • ROLLBACK
  • REBOOT

Output Schema

{
"intent":"CONFIG_PREVIEW",
"target":"Node-12",
"confidence":0.91
}

Confidence < 0.7 → clarification required

6.2 Reasoning Strategy

  1. Collect EMS data
  1. Correlate time, alarms, KPIs
  1. Apply telecom domain rules
  1. Generate explanation
  1. Suggest safe next steps

6.3 Hallucination Prevention

RiskControl
Fake alarmsEMS API only
Fake KPIsContext injection
Unsafe actionsGuardrail engine
OverconfidenceConfidence scoring

7. Prompt & Guardrail Design Summary

Prompt Rules

  • Read-first default
  • No silent execution
  • No invented data
  • Always explain

Guardrail Rules

  • LLM cannot bypass policy
  • Approval mandatory for writes
  • All actions logged

9. Security & Compliance Design

Security Controls

  • RBAC
  • Token-based auth
  • Encrypted APIs
  • No EMS credentials exposed to LLM

Compliance

  • Full audit trail
  • Action attribution
  • Config change history
  • AI decision explainability

10. Scalability & Reliability

Scalability

  • Stateless LLM calls
  • Horizontal orchestrator scaling
  • Async EMS calls

Reliability

  • Circuit breakers
  • Retry policies
  • Fallback to manual EMS
