LLM Prompt Architecture for EMS Vibe Coding Assistant

1. Architecture Goals

  • Convert natural language → EMS-safe actions
  • Enforce telecom domain rules
  • Prevent unsafe or unauthorized operations
  • Ensure explainable & auditable AI behavior
  • Support read, write, rollback workflows

3. System Prompt (Immutable)

Purpose

Defines non-negotiable rules for the LLM.

Example

You are EMS Vibe Coding Assistant.
You assistin managing a telecom Element ManagementSystem.
You must NEVERexecute destructive actionswithout approval.
You mustALWAYSexplain EMS termsin simplelanguage.
If uncertain, askfor clarificationor stayinread-only mode.
All actions must be auditable.

4. Domain Prompt (EMS Intelligence Layer)

Purpose

Inject telecom EMS knowledge.

Contents

  • EMS modules: PM, FM, CM, SM
  • KPI definitions & counters
  • Alarm taxonomy
  • Config parameter limits
  • SOPs & best practices

Example

EMS includes Performance, Fault,Configuration,andSystem Management.
Alarms have severity levels: Critical, Major, Minor,Warning.
Config changes mustvalidate parameter rangeand NE capability.
KPI degradation may correlatewith alarmsor recent config changes.

5. Context Prompt (Dynamic Runtime Context)

Purpose

Provide real-time EMS state.

Injected Data

  • User role & permissions
  • Target NE / Cell / Cluster
  • Time window
  • Active alarms
  • Recent config changes

Example

UserRole:NetworkEngineer(WriteAllowed)
TargetNode:Node-12
ActiveAlarms:HighCPU,LinkDown
LastConfigChange:TXPoweradjusted2hoursago

6. Task Prompt (Intent Understanding)

Purpose

Convert user text → structured intent.

Output Schema (JSON)

{
"intent":"CONFIG_CHANGE",
"target":"Node-12",
"parameters":{
"tx_power":"+2dB"
},
"confidence":0.92
}

Example Prompt

User request: "Increase TX power by 2dB on Node-12"
Identify intent, target, parameters,and confidence.

7. Safety & Policy Prompt (Guardrail Layer)

Purpose

Prevent unsafe actions.

Rules

  • Default read-only
  • Validate thresholds
  • Require approval for write ops
  • Block unknown parameters

Example

Is this action destructive?
Are parameterswithin allowed range?
Doesuserrole permit this action?
Ifnot,return BLOCKEDwith reason.

Output

{
"status":"REQUIRES_APPROVAL",
"risk_level":"MEDIUM",
"validation":"PASS"
}

8. Action Prompt (EMS API Mapping)

Purpose

Translate intent → EMS API calls.

Example Mapping

CONFIG_CHANGE → /ems/cm/updateParameter
ALARM_QUERY → /ems/fm/getAlarms
KPI_QUERY → /ems/pm/getKPI

API Payload (Generated)

{
"nodeId":"Node-12",
"parameter":"tx_power",
"value":"+2"
}

9. Execution Feedback Prompt

Purpose

Interpret API response.

Example

API Result:SUCCESS
Noderespondedin120ms
Noalarmstriggeredpost-change

10. Response Prompt (Human-Friendly Output)

Purpose

Explain outcome to user.

Rules

  • No raw API jargon
  • Explain impact & next steps
  • Provide rollback option

Example

TX power was increasedby2 dBon Node-12.
This may improve cell-edge coverage.
Nonew alarms were detected.
You canrollback this changeif needed.
